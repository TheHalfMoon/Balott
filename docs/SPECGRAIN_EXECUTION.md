# SpecGrain + Diffcipline Execution Model for Balott

**Status:** planning methodology

## Why this method

Balott contains several surfaces where a plausible implementation is not enough:

- rules can silently score the wrong winner;
- a bot can accidentally read hidden cards;
- reconnect can duplicate commands/cards;
- rank protection can create an exploit;
- a shuffle can be statistically or procedurally biased;
- a spectator endpoint can leak a hand;
- a voice recognizer can commit the wrong high-impact command.

SpecGrain is used to make each change small and bounded. Diffcipline is used to prevent `agent says done` from becoming completion authority.

References:

- https://github.com/TheHalfMoon/SpecGrain
- https://github.com/TheHalfMoon/Diffcipline

## 1. Root specification map

When implementation is authorized, initialize SpecGrain and create one root program spec with child workstreams corresponding to the roadmap phases.

Suggested roots:

```text
SG-BALOTT-CORE          P01-P04
SG-BALOTT-CLIENT        P05
SG-BALOTT-SOCIAL        P06/P11
SG-BALOTT-COMPETITIVE   P07/P12
SG-BALOTT-BOT           P08
SG-BALOTT-VOICE         P09
SG-BALOTT-LIVE          P10
SG-BALOTT-REALTABLE     P13
SG-BALOTT-COACH         P14
SG-BALOTT-BUSINESS      P15
SG-BALOTT-RELEASE       P16
```

Actual SpecGrain IDs should be generated by SpecGrain rather than invented in product code. The names above are planning labels.

## 2. Grain readiness

A leaf becomes executable only when it has:

- one explicit outcome;
- bounded in-scope/out-of-scope;
- dependencies satisfied;
- exact change surface estimate;
- acceptance conditions;
- evidence requirements;
- risk level;
- recovery/revert strategy;
- context budget/sources;
- security/privacy/fairness considerations where relevant;
- minimality rationale.

If a task still says `implement ranked` or `build bot`, it is not a Grain.

## 3. Example decomposition

Bad task:

`Implement teammate abandonment protection.`

Better recursive decomposition:

```text
Abandonment protection
  -> classify disconnect/abandon/server-fault terminal states
  -> represent innocent-teammate protection result
  -> apply visible Rank Point rule
  -> preserve streak/promotion state
  -> activate stand-in bot
  -> allow safe human rejoin
  -> detect reciprocal premade abuse candidate
  -> publish UI reason
  -> prove simulations/negative cases
```

Each leaf can then be independently implemented and proven.

## 4. Risk profiles

Map Diffcipline rigor to change risk.

### R0 — documentation/low-risk metadata

Examples:

- copy change;
- non-authoritative docs;
- source registry metadata.

Evidence: formatting/schema/link checks as applicable.

### R1 — ordinary product/UI behavior

Examples:

- non-critical profile surface;
- majlis history presentation;
- cosmetic store UI.

Evidence: focused tests, type/lint/build, accessibility/design checks.

### R2 — runtime/user-state behavior

Examples:

- presence/invites;
- voice command UI;
- club scheduling;
- replay viewer;
- account/session flows.

Evidence: focused integration tests, failure cases, platform checks.

### R3 — competitive authority / safety-critical game behavior

Examples:

- rules/scoring;
- shuffle/commit-reveal;
- match ledger;
- reconnect/ownership;
- Qayd validator;
- rating/abandonment policy;
- bot observation firewall;
- spectator hidden-state isolation;
- tournament manifest/referee authority.

Evidence should include exact diff review, focused + broader tests, negative/counterexample tests, property/fuzz/simulation evidence where relevant, and independent review.

## 5. Diffcipline policy direction

When the executable toolchain exists, initialize Diffcipline and declare repository-native commands rather than keeping a decorative policy file with tests that do not exist yet.

Expected principles:

- dependency manifest changes = review;
- lockfile changes = review;
- security/fairness critical directories require R3;
- verification never silently executes without explicit `--run`/CI policy;
- exact changed paths are compared to the Grain scope;
- no PASS when required verification did not run.

## 6. Proof matrix by subsystem

| Subsystem | Minimum proof families |
| --- | --- |
| Rules | fixtures, properties, fuzzing, replay determinism |
| Shuffle | commitment negative tests, deterministic verifier, statistical simulation, crypto review |
| Match runtime | integration, retry/idempotency, fault injection, restart/ownership tests |
| Qayd | positive/negative/out-of-window/missed-claim/bot-denial tests |
| Ranked | simulation, calibration, abandon/protection abuse scenarios |
| Bot | frozen tournament harness, hidden-info denial, legality, latency |
| Voice | Arabic/noise corpus, false execution, latency, device/battery, fallback policy |
| Spectator | hidden-state access negative tests, delay policy, replay consistency |
| Clubs/152 | authorization, deterministic bracket/manifest, dispute lifecycle |
| Real Table | offline/local provenance, sync conflict, no official-authority impersonation |
| Coach | active-match denial, factual-stat validation, explanation evaluation |
| UI | Impeccable critique/detect where supported, accessibility, device visual/interaction checks |

## 7. Design proof using Impeccable

Impeccable is part of the product-quality loop, not the authority for game correctness.

For major UI surfaces:

1. load `PRODUCT.md` and `DESIGN.md`;
2. use `shape` before a new direction;
3. implement bounded surface;
4. use `critique` with fresh review context;
5. run deterministic `detect` where supported;
6. capture rendered interaction evidence on target device/browser;
7. accessibility and gameplay acceptance remain separate checks.

A clean Impeccable report does not prove rules/fairness.

Reference: https://impeccable.style

## 8. Source-aware WorkPackets

Every Grain that studies/adopts external source material should include context sources with immutable revision/provenance when possible.

Do not feed the executor the entire 100+ source landscape. Context selection should include only the exact source(s) relevant to that Grain plus canonical Balott contracts.

Examples:

- voice VAD Grain: Balott voice contract + exact Silero/TEN/sherpa candidates;
- P2P Grain: Balott Real Table authority boundary + exact Iroh source;
- design Grain: `PRODUCT.md`, `DESIGN.md`, target components, Impeccable reference;
- abandonment Grain: ranked contract + relevant simulations/tests, not all social docs.

## 9. Donor tournaments

When several authorized sources solve the same bounded problem, use a predeclared donor tournament instead of taste.

Example voice-runtime tournament dimensions:

- Arabic command accuracy;
- false execution;
- latency;
- memory;
- binary/model size;
- battery/thermal;
- offline operation;
- platform coverage;
- security/supply-chain surface.

Freeze candidates/revisions, devices/corpora, metrics, and selection rule before running. Preserve losers.

## 10. Implementation handoff rule

A future builder prompt should not contain `finish Balott` as one unbounded task.

It should say, in effect:

> Reverify canonical main, identify the next dependency-eligible SpecGrain leaf, execute only its WorkPacket, run required Diffcipline proof, preserve evidence, then advance to the next eligible leaf if and only if governance permits it.

This keeps the ambitious roadmap compatible with high execution quality.
